# BidWise — 요구사항

> **무엇을 만들고 무엇을 만들지 않는지 적는 문서다.** 우선순위는 M(MVP) / S(MVP 직후) / L(나중).
> 진행 상황은 [PLAN](PLAN.md), 화면 규칙은 [DESIGN](DESIGN.md), API는 [ARCHITECTURE](ARCHITECTURE.md) 3장, 왜 이 스택인지는 [decisions/](decisions/README.md).

---

## 1. 목적

나라장터에서 공사 입찰 데이터를 **수집**하고, 지역·공종별 낙찰률을 **분석**해, 지도와 차트로 **시각화**하고, 조건별로 **필터링**해 볼 수 있는 서비스.

적산(공사비 산정) 분야를 데이터 관점에서 이해하기 위한 학습 프로젝트다. 입사 뒤에는 실무에서 얻은 지식으로 되돌아와 검증한다 (6장).

**핵심 지표**: 낙찰률 = 낙찰금액 ÷ 예정가격 × 100. 직접 계산하지 않고 API의 `sucsfbidRate`를 쓴다 ([DATA_MODEL](DATA_MODEL.md) 3.3절).

### 왜 지도인가

유사 서비스(모두입찰, 지투비플러스 등)를 조사해 보니 실무 입찰 서비스에는 지도 시각화가 없다. 놓쳐서가 아니라 목적이 달라서다.

| | 실무 서비스 (모두입찰 등) | BidWise |
|---|---|---|
| 주 사용자 | 입찰에 실제 참여하려는 업체 | 시장 전체를 조망하려는 학습자 |
| 핵심 질문 | "이 공고에 얼마를 써야 낙찰될까?" | "전국적으로 낙찰 경향이 어떻게 분포하는가?" |
| 제공 형태 | 리스트, 순위표, AI 챗봇, 계산기 | 지도, 집계 차트 |

경쟁이 아니라 같은 데이터를 다른 각도에서 보는 도구다. 지역별 지도(UC2)가 이 프로젝트의 정체성이라 일정이 밀려도 버리지 않는다 ([PLAN](PLAN.md) 6장).

## 2. 누가 무엇을 하는가

유즈케이스를 가르는 기준은 "누가 이 동작을 시작시키는가"다.

| # | 유즈케이스 | 누가 | 비고 |
|---|---|---|---|
| UC1 | 대시보드 요약 조회 | 사용자 | 진입 시 최초 표시 |
| UC2 | 지역별 지도 조회 | 사용자 | 낙찰 완료/대기도 함께 |
| UC3 | 공종별 차트 조회 | 사용자 | |
| UC4 | 기간·지역 등 필터링 | 사용자 | UC1 ~ UC3, UC5에 모두 영향 |
| UC5 | 지도 클릭 → 공고 목록 | 사용자 | UC2가 화면에 있어야 성립 |
| UC6 | 입찰 데이터 수집·처리 | 스케줄러 (지금은 수동 명령) | 수집→정제→적재를 한 목표로 묶음 |

사용자가 보는 화면(UC1 ~ UC5)은 UC6이 미리 채워 둔 데이터를 조회할 뿐이다. 흐름은 [ARCHITECTURE](ARCHITECTURE.md) 2장.

## 3. 만들 기능

### 3.1 수집

| 번호 | 기능 | 우선 |
|---|---|---|
| F-01 | 나라장터 입찰공고 수집 (공사만) | M |
| F-02 | 낙찰결과 수집, 공고에 연결 | M |
| F-03 | 면허제한정보 수집 (공종 분류 2차 출처) | M |
| F-04 | 중복 공고 처리 — `(공고번호, 차수)` 기준 UPSERT | M |
| F-05 | 수동 수집 명령, 긴 기간은 하루씩 저장 | M |
| F-06 | 시간 초과 · 연결 끊김 재시도 | M |

## 4. 하지 않을 것

- **입찰가 추천 · 낙찰 예측** — 실무 도구의 일이다. 분석 결과를 실제 입찰 의사결정 근거로 쓰지 않는다 (README).
- **로그인 · 계정** — MVP에 없다. 조회 API도 인증 없음.
- **조회 시점 실시간 호출** — 미리 수집한다 ([0003](decisions/0003-etl-store-first.md)).
- **낙찰률 직접 계산** — API 제공값을 쓴다.
