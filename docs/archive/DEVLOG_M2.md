## 2026-10-26 (월) — 공종 분류에 면허제한정보 추가: 업종 없는 공고 정확도 약 96% (회사 PC)

> 바로 아래 사전 검증의 추천안을 사용자 확인 후 구현했다.

### [설계] 분류 순서: 업종 → 면허 → 공고명 키워드 → 분류 못함

- `lcns_lmt_nm`(첫 면허 이름) 컬럼 — 마이그레이션 `0003`. 원본으로 저장해서 규칙을 고쳐도 API 없이 재분류된다
- 면허가 여러 개면 공고서 순서(제한그룹번호·순번)로 첫 번째. **순번은 숫자로 정렬**한다 ("10" < "2" 문자열 함정)
- 면허가 "기타"(어장정화ㆍ정비업 등)면 공고명 키워드를 먼저 본다
- 수집(`collect.py`)할 때 하루마다 면허제한정보도 받는다 (999건씩 하루 1~3번). 그 전에 모은 공고는 `python -m app.backfill_license`로 채운다
- 사전 검증에서 겪은 "페이지 크기가 조용히 10이 되는" 일을 막으려고, 첫 페이지가 요청보다 적게 왔는데 남은 게 있으면 `_fetch_all`이 바로 멈춘다

### [DB] 결과 (실제 PostgreSQL, 2026-09-26 ~ 10-25, 공고 10,285건)

- 백필: 호출 **53번**, 면허 채운 공고 9,312건, 재분류로 6,644건 고침
- 업종 없는 공고 7,453건 중 면허 있음 **89.3%**
- 업종·면허가 둘 다 있는 2,657건에서 대분류 일치 **98.4%** (하루치 139건 측정 96.4%보다 높게 나옴) → 면허 분류의 정확도 추정치

| 출처 | 전 | 후 |
|---|---|---|
| main_cnstty (업종) | 2,832 | 2,832 |
| license (면허) | — | **6,644** |
| keyword (추정) | 6,334 | 677 |
| none (분류 못함) | 1,119 (10.9%) | **132 (1.3%)** |

- 업종 없는 공고 중 분류된 것의 예상 정확도: **95.9%** (= 면허 6,644건 × 98.4% + 키워드 677건 × 71.1%)
- **정직하게 적을 것**: 진짜 대상 집단(업종 없는 공고)에서 면허를 정답으로 다시 재 보니 키워드 규칙 정확도는 **71.1%**로, 업종 있는 공고로 잰 79%보다 낮았다. 규칙을 다듬은 데이터로 잰 숫자는 실제보다 좋게 나온다
- 공종 순위가 바뀌었다: 건축 2,063 → **3,135**(1위), 토목 2,842 → 2,514. 키워드 추정이 건축 공사를 토목으로 끌어가고 있었다. 토목의 "추정" 건수는 2,267 → 195
- 오늘 입찰공고정보서비스 누적 약 400/1,000건

**배운 것**
정확도를 올리는 가장 큰 한 걸음은 규칙을 다듬는 게 아니라 **더 나은 원천 데이터**를 찾는 것이었다. 응답에 이미 있던 `indstrytyLmtYn = Y` 한 칸이 단서였다.

## 2026-10-26 (월) — 공종 분류 정확도 90% 이상 사전 검증 (회사 PC)

> 목표: 업종이 없는 공고의 분류 정확도를 79% → 90% 이상으로. 구현 전 사전 검증 결과.

### [외부API] 사전 검증에서 발견 — 면허제한정보에 수의계약 공고의 업종이 있다

**발견**
공고 응답의 `indstrytyLmtYn`(업종제한 여부)이 업종(`mainCnsttyNm`)이 빈 수의계약 공고에서도 `Y`였다.
업종 이름은 같은 서비스의 별도 오퍼레이션 **`getBidPblancListInfoLicenseLimit`(면허제한정보)** 의 `lcnsLmtNm`에 있다.

**2026-10-20 하루치 측정** (공고 571건)
- 면허제한 정보가 붙은 공고: 508/571 (89%). **업종이 없는 공고 중 369/423 (87%)**
- 업종·면허가 둘 다 있는 139건에서 대분류 일치 **96.4%** → 추정이 아니라 믿을 만한 정보원
- 같은 업종 없는 공고(진짜 대상)에서 키워드 규칙: 분류율 84.8%, 정확도 78.3% (기존 측정 79%와 비슷)
- 면허가 여러 개라 대분류가 섞인 공고 29건: "첫 면허"와 "다수결" 둘 다 27/29 일치 → 단순한 "첫 면허"로 충분
- 응답에 물품·용역도 섞여 온다 (하루 1,886행 중 공사 644) → `bsnsDivNm == "공사"`로 거른다

### [설계] 사전 검증 — 공고명만으로는 80%대 중반이 한계

| 방식 | 분류율 | 정확도 |
|---|---|---|
| 지금 키워드 규칙 | 85% | 79.6% |
| 단어 통계 학습(Naive Bayes, 5겹 교차검증) | 100% | 80.7% |
| 단어 통계, 확신도 0.95 이상만 | 89% | 85.4% |
| 키워드와 단어 통계가 같을 때만 | 64% | 92.1% |

정답지(업종)가 "업체의 면허"라 공고 내용과 어긋나는 경우가 섞여 있어서, 공고명만으로는 90%를 넘기려면 분류율을 크게 버려야 한다.
→ **면허제한정보를 2차 출처로 넣는 쪽이 정확도와 분류율을 둘 다 지킨다.**

### [외부API] 실수 — `numOfRows=1000`이 조용히 10으로 바뀌어 호출 189번을 썼다

**증상**
면허제한정보 하루치(1,886행)를 `numOfRows=1000`으로 받으려 했는데 189페이지가 돌았다.

**원인**
이 API의 페이지 최대 크기는 **999**다. 1000 이상을 주면 에러 없이 기본값 10으로 돌아간다. 반복문이 첫 응답의 실제 건수를 확인하지 않았다.

**해결**
`numOfRows=999`로 다시 확인: 999건이 온다 (하루치 2번이면 된다). 오늘 입찰공고정보서비스 누적은 약 340/1,000건으로 한도 안.

**배운 것**
처음 써 보는 API의 페이지 크기는 **첫 응답의 실제 건수로 확인한 뒤** 반복한다. 사전 검증에서 "몇 번 부르게 되나"는 응답을 보고 계산해야 맞다.

## 2026-10-26 (월) — M2 완료: 지역 정규화 · 공종 분류 · 집계 쿼리 (회사 PC)

### [설계] 구현 내용

- 컬럼 3개(`region_normalized`, `category`, `category_source`) + `ix_region_normalized` — 마이그레이션 `0002`. 원본은 그대로 두고 정제값을 옆 칸에 적는다
- 대분류 11개: 건축 · 토목 · 전기 · 통신 · 기계설비 · 소방 · 조경 · 산림 · 환경 · 국가유산 · 기타 (분류 못하면 NULL, 집계에선 "미분류")
- 수집할 때와 재분류할 때 같은 함수(`transformer/announcement.py`의 `classification_of`)를 쓴다 — 규칙이 한쪽만 바뀌는 사고 방지

- 집계 쿼리 3개(`bid_repo.get_summary` / `get_region_stats` / `get_category_stats`): 전부 LEFT JOIN, 기간 끝날 포함("다음 날 0시 미만"). 공종별은 추정 건수(`keyword_count`)를 같이 준다

**키워드 규칙 다듬기** (업종 있는 공고 2,832건 = 정답지)
- 다리 이름 패턴(`~교 보수`)을 더했더니 토목→건축 오분류는 72 → 35로 줄었지만, 건축→토목이 96 → 125로 늘었다
- 원인을 세어 보니 "OO초 **외 1교**(옥구초) 지붕보수" — "학교 1곳 더"라는 표현이 다리 패턴에 걸렸다 → 숫자 뒤 "교"는 제외
- 최종: 분류율 85.1%, 분류한 것 중 정확도 **79.3%**. 남은 오류엔 "건축 업종 업체가 도로 공사를 맡은" 것처럼 정답지 자체가 애매한 경우가 섞여 있어 여기서 멈췄다

### [DB] PostgreSQL의 `SUM(BIGINT)`는 Decimal로 온다 — SQLite 테스트로는 안 보였다

**증상**
실제 DB로 요약 집계를 확인하는 스크립트에서:
```
TypeError: unsupported operand type(s) for /: 'decimal.Decimal' and 'float'
```

**원인**
PostgreSQL은 `SUM(bigint)`의 결과 타입이 `numeric`이라 파이썬에선 `Decimal`이 된다. 테스트용 SQLite는 `int`를 돌려줘서 pytest 94개가 다 통과했다.

**해결**
`get_summary`에서 `total_budget_amt`를 `int`로 바꿔 돌려준다 (API 명세가 int).

**배운 것**
테스트 DB와 실제 DB는 "같은 SQL, 다른 반환 타입"일 수 있다. 실제 DB 확인 단계를 건너뛰지 않는 이유.

### [DB] M2 완료 기준 확인 (실제 PostgreSQL, 2026-09-26 ~ 10-25)

- 0002 적용 → 재분류 1회차 10,285건 고침, 2회차 **0건** (반복해도 같음). 지역 못 정함 0건
- 지역별 GROUP BY: `서울 / 전체 676 / 완료 310 / 평균 91.69%` 형태로 16개 지역 전부 나온다
- 출처: `keyword` 6,334 · `main_cnstty` 2,832 · `none` 1,119 — 완료 기준(keyword·main_cnstty 둘 다 존재) 충족
- 공종별 상위: 토목 2,842(추정 2,267) · 건축 2,063 · 전기 1,133 · 미분류 1,119 · 산림 1,083

### [설계] M4를 위한 발견 — 지역별 평균 낙찰률이 90.26~91.69%에 몰려 있다

16개 지역 평균의 차이가 1.4%p 안이다. `06_ui_ux.md`의 "5단계 블루 스케일"을 고정 구간(예: 80~100%를 5등분)으로 나누면 **전국이 거의 한 색**으로 칠해진다.
→ M4에서 색 구간은 실제 값 범위(최솟값~최댓값) 또는 분위수로 나누고, 범례에 실제 수치를 적어야 한다. 차이가 작다는 사실 자체도 화면에서 정직하게 보여 줄 거리다.
(수의계약 편향 — 위 M1 항목 — 도 여전히 있다. 경쟁입찰 결과가 채워지면 분포가 달라질 수 있다)

- 그대로 쓰면 차트 막대가 47개가 되고, 키워드 폴백이 업종 이름을 맞혀야 해서 둘의 분류 체계가 어긋난다 → **업종 → 대분류(약 11개) 매핑**이 필요하다
- 업종이 있는 공고는 **정답지**로 쓸 수 있다: 키워드 규칙을 그 공고명에 돌려 정확도를 잰다

| 키워드 규칙 | 업종 있는 공고(정답지)에서 분류율 | 분류한 것 중 정확도 | 업종 없는 공고 7,453건 분류율 |
|---|---|---|---|
| 초안 | 81.1% | 78.2% | 76.7% |
| 1회 보완 (재선충·덩굴·차선도색·복구 등 추가) | 84.9% | 78.7% | 85.0% |

- 가장 많이 틀리는 쌍은 토목↔건축 (예: "OO교 시설물 보수공사"가 `보수` 때문에 건축으로 감). 다리 이름(`~교`) 같은 패턴을 더하면 줄일 수 있지만, 공고명만으로는 80%대 중반이 현실적인 한계로 보인다
- 정답지가 경쟁입찰 위주라, 수의계약 공고에서의 정확도는 이 수치와 다를 수 있다
- 규칙은 계속 고치게 된다 → 저장된 공고 전체를 API 호출 없이 **다시 분류하는 명령**이 처음부터 필요하다 (`03_architecture.md` 7장 "재분류 배치 스크립트")

## 2026-10-26 (월) — 작업 방식: 구현 전 사전 검증 추가

### [설계] "설계대로 만들었다고 치면?"을 구현 전에 먼저 따져 본다

**상황**
M1에서 실제 API 응답을 먼저 확인한 덕분에 낙찰정보 `inqryDiv`를 잘못 쓸 뻔한 걸 막았다.
하지만 한 달치 일괄 수집의 시간 초과(호출 47번 버려짐)는 못 막았다. 페이지 수(52), 커밋 단위(마지막 1번), 재시도 없음은 코드를 쓰기 전에 다 알 수 있었다.

**결정**
본격 구현 전에 설계 요약 → 실제 데이터로 미리 돌려 보기 → 규모·실패 따져 보기 → 대안 비교 → "예상 결과 / 발견한 문제 / 보완안" 보고를 거친다. 규칙은 `CLAUDE.md` "작업 규칙"에 적었다.
M2부터 적용한다. 예: 공종 키워드 규칙을 만들기 전에 DB의 공고명 10,285건에 먼저 돌려 분류율과 오분류 사례를 본다.

**배운 것**
"만들고 나서 확인"은 실패를 늦게 알게 한다. 싸게 미리 볼 수 있는 것(데이터 양, 실패 지점)은 만들기 전에 본다.
