## 2026-10-26 (월) — M1 완료: 낙찰정보 수집 · 공고 연결 · 한 달치 적재 (회사 PC)

### [외부API] 낙찰정보의 `inqryDiv=1`은 "결과 등록일"이다 — 공고와 기간을 맞추려면 `2`

**증상**
입찰공고와 같은 기간(2026-10-20)으로 낙찰정보를 `inqryDiv=1`로 불렀더니, 받은 결과 10건이 DB의 공고와 **하나도** 맞지 않았다.

**원인**
`inqryDiv`의 뜻이 API마다 다르다. 입찰공고의 `1`은 공고게시일시인데, 낙찰정보의 `1`은 결과 등록일시(`rgstDt`)다.
그날 등록된 결과는 대부분 며칠~몇 주 전에 올라온 공고의 것이다.

**해결**
세 값을 한 번씩(10건) 불러 DB의 공고와 대조했다: `1` → 0/10, `2` → 10/10, `3` → 1/10. `2`가 공고일시 기준이다.
`client.py`에 `RESULT_INQRY_DIV = "2"`로 두고 근거를 주석으로 남겼다.

**배운 것**
이름이 같은 파라미터라도 API가 다르면 뜻이 다를 수 있다. 문서보다 "저장된 데이터와 맞춰 보기"가 빠르고 확실했다.

### [설계] 낙찰정보 행은 재입찰번호로 더 쪼개진다 → 최종 결과 하나만 저장

낙찰정보 행은 (번호, 차수) 말고도 `bidClsfcNo`(분류)·`rbidNo`(재입찰)로 나뉘어 온다. 표본에서 `rbidNo=001`을 1건 봤다.
ERD는 공고 1 : 결과 0..1이므로(DB의 UNIQUE가 강제), **재입찰번호가 가장 큰 = 최종 결과**만 남긴다 (`transformer/result.py`의 `pick_final_results`).
`02_erd.md` 6장의 "유찰/재공고 취급" 미결정 항목을 이 기준으로 결정 처리했다.

### [외부API] 한 달을 한 번에 받다가 48페이지째에서 ReadTimeout — 47번의 호출이 버려졌다

**증상**
```
requests.exceptions.ReadTimeout: HTTPSConnectionPool(host='apis.data.go.kr', port=443): Read timed out. (read timeout=10)
```
2026-09-26~10-25를 한 번에 수집하던 중, 공고 52페이지 가운데 48페이지째에서 멈췄다. 커밋이 마지막에 한 번이라 DB에는 아무것도 안 남았다.

**원인**
뒤쪽 페이지일수록 응답이 느렸다 (1페이지 약 1초 → 47페이지 약 10초). 타임아웃 10초에 걸렸고, 재시도가 없었다.

**해결**
- `_call_api`: 시간 초과·연결 끊김만 2초 → 4초 쉬고 최대 3번 시도, 타임아웃 30초. 4xx·`resultCode` 오류는 다시 불러도 같으므로 재시도하지 않는다 (호출 한도 낭비 방지)
- `collect_by_day`: 긴 기간을 **하루씩** 수집·커밋. 하루치가 2~4페이지라 깊은 페이지가 없고, 실패해도 그날만 다시 돌리면 된다
- 같은 한 달을 다시 돌려 117번 호출로 끝났다 (오류 0)

**배운 것**
여러 번의 외부 호출을 한 트랜잭션에 묶으면, 마지막 한 번의 실패가 앞의 성공을 전부 지운다. 커밋 단위를 "다시 돌리기 싼 단위"로 자른다.

### [DB] 입찰공고 UPSERT — `(bid_ntce_no, bid_ntce_ord)` 기준 `ON CONFLICT DO UPDATE`

**결정**

  - 모르는 날짜 형식은 `None`으로 덮지 않고 `ValueError` — 조용히 비우면 기간 필터에서 공고가 사라져도 모른다

  - 한 묶음 안에 같은 키가 두 번 있으면 PostgreSQL이 `cannot affect row a second time`으로 묶음 전체를 거절한다 → 키가 같으면 나중 것만 남긴다
  - 1,000행씩 나눠 보낸다 (문장 하나에 파라미터 65,535개 제한)
  - 실제 DB는 PostgreSQL, 테스트는 SQLite라 연결된 DB에 맞는 `insert`를 고른다 (두 DB 모두 `on_conflict_do_update` 문법이 같다)
- `app/collect.py`: 수집 → 변환 → 저장을 잇는 수동 실행 스크립트. `python -m app.collect 202610200000 202610202359`
- pytest 21개 (변환 6, UPSERT 7 추가). 테스트용 응답에 **실제 응답 원문**(`tests/fixtures/announcements_real.json`, 3건, 필드 143개 그대로)을 추가했다

## 2026-10-24 (토) — 재정비 2단계: 기반 코드 정리

### [환경설정] 버전을 안 고정했더니 SQLAlchemy 2.1이 깔리고, 기본 DB 드라이버가 바뀌어 있었다

**증상**
새 venv에 `requirements.txt`를 설치하고 DB에 접속하자마자 실패했다.
```
ModuleNotFoundError: No module named 'psycopg'
```
psycopg2-binary는 분명히 설치돼 있었다.

**원인**
`requirements.txt`에 버전이 없어서 그날의 최신인 SQLAlchemy 2.1.6이 깔렸다.
SQLAlchemy 2.1부터 `postgresql://` 주소의 기본 드라이버가 psycopg2에서 **psycopg(3)**로 바뀌었다.
M0 때(2.0)는 같은 주소가 psycopg2를 찾았다.

**해결**
드라이버를 psycopg 3(`psycopg[binary]`)으로 바꾸고 모든 패키지 버전을 `==`로 고정했다.
`.env`의 `postgresql://...` 주소는 그대로 쓸 수 있다.

**배운 것**
버전을 고정하지 않으면 "같은 requirements.txt"가 설치하는 날마다 다른 환경이 된다. 기기가 여러 대면 더 그렇다.

### [설계] 기반 코드 정리 내용

- `app/config.py`: `.env` 읽기를 한 곳으로 (pydantic-settings). import 시점이 아니라 처음 쓸 때 읽어서, 테스트가 환경변수로 값을 바꿔 끼울 수 있다
- `app/database.py`: engine·Session 생성을 한 곳으로
- `app/models.py`: SQLAlchemy 2.0 스타일(`Mapped[...]`). 테이블 구조는 그대로
  - `fetched_at`은 UTC로 저장한다. 컬럼이 `timestamp`(시간대 없음)라서, 시간대가 붙은 값을 넣으면 PostgreSQL이 세션 시간대(한국)로 바꿔 9시간 어긋난다 → 시간대를 떼고 넣는다
- **Alembic**: `0001_initial_schema` = M0 테이블 그대로. 오프라인(`--sql`)으로 뽑은 PostgreSQL DDL이 M0 구조와 같은 것을 확인했다. `create_tables.py`는 삭제
  - M0 방식으로 테이블이 이미 있는 기기는 `alembic stamp 0001` 한 번 → 이후 `alembic upgrade head`
- `client.py`: 인증키를 `_call_api`에서 한 번만 붙임, `print` → `logging`
- **pytest 8개**: 클라이언트 6개(가짜 응답 — 인증키 전달, 에러 코드, 페이징, `items=""`, 차수), 마이그레이션 2개(임시 SQLite에 끝까지 적용한 결과 == models.py, 되돌리기)
  - 마이그레이션 테스트가 진짜 차이를 잡는지, 모델에 컬럼을 하나 몰래 추가해서 실패하는 것까지 확인했다

**실제 PostgreSQL 검증** (`D:\_dev` 기기, PostgreSQL 18.4, 세션 시간대 Asia/Seoul)
- M0 방식으로 만든 테이블이 있었다(0행, `alembic_version` 없음). stamp 전에 실제 구조와 모델을 대조 → 차이 없음
- `alembic stamp 0001` → `alembic upgrade head` → `alembic current` = `0001 (head)` → `alembic check` = "No new upgrade operations detected."
- 실제로 써 보고 rollback (데이터는 남기지 않음):
  - 같은 번호에 차수 `000`·`001` 공존 OK, 같은 `(번호, 차수)` 다시 넣으면 `UniqueViolation`
  - 한 공고에 낙찰결과 2개 → `UniqueViolation` (1:0..1이 DB에서 강제됨), 결과 없는 공고의 `.result`는 `None`
  - `NUMERIC(6,3)`에 `87.745`, `BIGINT`에 123억 그대로 저장
  - `fetched_at` 저장값과 UTC 현재 시각의 차이 0초 → 한국 시간대 세션에서도 9시간 어긋나지 않음

**아직 못 한 것**
- 노트북·학교 PC는 각자 위 순서로 맞춰야 한다 (현재 상태 표 참고)
- 테스트용 응답 JSON(`tests/fixtures/`)은 뼈대만 본뜬 예시다. 다음 실제 호출 때 응답 원문으로 바꾼다
- 이 기기의 `.env`는 `postgres` 슈퍼유저로 접속한다. 다른 기기처럼 `bidwise_app` 전용 유저를 쓸지는 나중에 정한다

### [외부API] Encoding 인증키를 `params`에 넣으면 이중 인코딩된다 → 키 재발급으로 해결

**증상**
`.env`에 있던 키가 `%3D`로 끝나는 Encoding 키였다. `requests.get(url, params={"serviceKey": key})`는
값을 자동으로 URL 인코딩하므로 `%`가 다시 `%25`로 바뀌어 인증이 실패한다.

**원인**
공공데이터포털 키는 이미 인코딩된 형태(Encoding)와 원본 형태(Decoding)가 있는데,
`params` 딕셔너리는 "아직 인코딩 안 된 값"을 가정한다.

**해결**
포털 UI가 바뀌어 Decoding 키 표시를 찾지 못했고, 대신 **일반 인증키를 재발급**받았다.
재발급 키로 `params` 방식 호출이 정상 동작한다 (`client.py`가 이 방식).
- 일반 인증키는 **서비스별이 아니라 계정당 하나**다. 재발급하면 입찰공고·낙찰정보 두 서비스 화면의 키가 함께 바뀐다
- 예전 `%3D` 키는 폐기됨

**배운 것**
외부 API 인증이 실패하면, 파싱하기 전에 `response.url`과 `response.text` 원문부터 눈으로 본다.
`%25`가 보이면 이중 인코딩이다.

### [외부API] `bidNtceNo`만으로는 공고가 유일하지 않다 — 정정공고는 차수만 오른다

**증상**
페이징 검증 스크립트에서 `bidNtceNo` 중복이 발견돼, 처음엔 페이징 버그를 의심했다.

**원인**
버그가 아니었다. 정정·재공고가 나가면 `bidNtceNo`는 그대로이고 `bidNtceOrd`만 오른다.
```
R26BK01705200 | 차수=000 | 외도수영장 개보수 공사
R26BK01705200 | 차수=001 | 외도수영장 개보수 공사
```
공고명도 거의 그대로 유지된다.

**해결**
유일성 판단 기준을 `(bidNtceNo, bidNtceOrd)` 조합으로 바로잡았다.
M0에서 만든 `UniqueConstraint("bid_ntce_no", "bid_ntce_ord")`와 MILESTONES M1의 UPSERT 기준이 맞다는 것을 실제 데이터로 확인했다.

**배운 것**
설계 단계에서 예상한 제약은, 실제 데이터에서 그 패턴을 직접 찾아봐야 확신할 수 있다.

### [환경설정] 기기 3대에서 작업할 때의 함정
